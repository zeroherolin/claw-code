When `true` and Claude Code's managed settings name a corporate launcher in `processWrapper` or `env.CLAUDE_CODE_PROCESS_WRAPPER`, the Code tab starts the app's Claude Code through it: on this device (managed-settings file or MDM profile, never server-managed), and, for an SSH session, through the one in the host's managed-settings files (`/etc/claude-code`; `/Library/Application Support/ClaudeCode` on macOS). Either way it is handed none of the app's inference credential (claude.ai sign-in, provider key, token, auth header or credential file) and reads no stored login or ambient cloud credential of this device (over SSH, the host account's own environment still applies); the launcher must put one in its environment — `ANTHROPIC_BASE_URL` with `ANTHROPIC_AUTH_TOKEN` or `ANTHROPIC_API_KEY`, or, for the Bedrock, Vertex or Foundry routing the app leaves set (`CLAUDE_CODE_USE_*`; override to switch), that provider's keys or credential file — or the start fails; it makes no non-essential Anthropic calls. The third-party connection test and title generation start directly. An unusable launcher, an unreadable host settings file or another Claude Code version refuses or ends the session with an error. Device launcher: macOS and Linux (ignored on Windows); SSH hosts: Linux or macOS, from any device; never WSL or Cowork; both deployment modes.

Unset or `false` (default): the app never reads that setting and starts Claude Code directly, with its own credential. A change applies at the next Claude Code start on third party (a served value once fetched) and at the next app launch on a claude.ai install (profile or local configuration file).

The key is in the app-behavior group (`disableAutoUpdates`, …): a profile that sets any group key is the only source read for all of them — set it in the profile, with every group key you need, when the profile sets any of them or the launcher must hold against the device's own user; else in the admin console or configuration server.
