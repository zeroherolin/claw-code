@internal The turn so far, in conversation order: the user's message, any [assistant, tool_result] rounds already answered elsewhere, and last an assistant message (thinking blocks with their signatures, text, and the tool_use blocks to run). Every message carries a uuid, kept as the transcript line's; none of the messages, and none of the tool_use ids they hold, may already be in the conversation — the turn is appended once, whole, never merged with lines already there (except as tool_use_ids describes for a turn that runs nothing). No two assistant messages share a message id, among these or with the conversation, with one exception, for a worker whose turn_handoff entry has shared_message_id: an assistant message that holds tool_use blocks only may repeat the id of the assistant message before it where every message between them, at least one, holds only tool_result blocks for that earlier message's calls. The two are then sent to the model as one message, its calls followed by their results, so a client does this only for calls of one Messages API response that it ran one after another. A request that names calls to run is refused (invalid_handoff) unless its first message is a user message, not empty and not a tool_result.
